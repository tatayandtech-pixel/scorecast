**Real bug caught and fixed live in production this cycle (2026-07-09)**: the web mirror's score buttons could enter a self-sustaining write loop on iOS Safari — replacing the tapped button's DOM node (which happened on every score update, since our own write immediately echoed back through our own listener) could get an in-flight click re-targeted onto the new element, firing another write, rebuilding again, indefinitely, with no further taps needed. Reproduced against a live session (climbed into the tens of thousands within minutes), confirmed the Android app wasn't the source (force-stopped it mid-runaway, no effect — stopped only when the iPhone tab was closed), fixed by no longer rebuilding score buttons except when the sport actually changes, deployed, and verified stable with repeated taps landing exactly once each. Worth remembering as a general lesson for this codebase: never destructively rebuild a DOM element in direct response to its own click on that same event tick.

**Real bug found and fixed on-device this cycle (2026-07-15)**: the in-game screen's sliding scoring panel (`LiveOverlay` in `MainActivity.kt`) had no bottom clearance from the fixed bottom-right action row (battery/Hide panel/End match), which is drawn on top of it. On a shorter-aspect-ratio physical device, the Period/Clock rows rendered underneath those floating buttons, and touch dispatch went to whichever floating element was on top instead of the intended clock control — reproduced live: a tap aimed at "Start" instead advanced the Period stepper once and opened the End Match confirmation dialog another time. Fixed by giving the panel's scrollable content 64dp of bottom padding so its viewport stops above the floating row (mirroring the existing top-clearance `Spacer(40.dp)` pattern already used for the top bar). Trade-off: the panel no longer auto-scrolls to the clock, so on short screens it now sits below the fold and needs a manual scroll to reach — but it is then reliably tappable, confirmed via direct on-device tap producing correct start/stop transitions with no accidental Period/End-Match triggers.

**Two more real bugs caught and fixed live this cycle (2026-07-16), both found via actual Android↔Android pairing on two physical devices (not just code review)**:
1. **Runaway score-write feedback loop between paired devices** (`FirebaseSessionSync.kt`) — `attachListener()`'s `onDataChange` toggled a boolean `applyingRemote` flag true/false around applying a remote update, meant to stop the local-change collector from re-pushing that same echo. But the collector runs in a separately-launched coroutine reading `GameStateHolder`'s `StateFlow`, so the flag was already back to `false` by the time the collector actually observed the emission — the "local" diff it then computed got pushed straight back to Firebase as a fresh increment. Reproduced live: `awayScore` climbed past 2 million in under a minute across two paired devices before both apps were force-stopped to break the loop. Fixed by tracking the identity of the last-applied remote `GameState` object instead of a timing-dependent flag — the collector now skips a push only when the emission is referentially the exact remote object it just received, which has no race window. Verified: repeated pairing + scoring across both devices afterward with no runaway.
2. **Team name edits not saving** (`ScoringPanel.kt`) — the team-name `OutlinedTextField` pushed to `GameStateHolder`/Firebase on every keystroke, and each write's own echo (a full-state overwrite via `applyRemote`) could arrive mid-typing and clobber characters typed after that keystroke, landing on a stuck partial value (reproduced live: a name landed stuck at `"AW"` instead of the full typed name). Fixed by buffering keystrokes in local Compose state and committing to `GameStateHolder` (and thus Firebase) only on focus loss, removing the per-keystroke race entirely — also arguably better UX, since other viewers no longer see a name mid-edit. Verified on-device after the fix.

## Known deviation from spec
Spec §12 calls for `:streaming`, `:overlay`, `:capture`, `:core-state` etc. as separate Gradle modules. The codebase is currently a single `:app` module (package `com.scorecast.app`) — no module split has been done. Flag this if a future session wants to enforce the module boundary; it hasn't blocked anything so far.

## Phase discipline
- The status section above is the reference for what's done vs. open — don't re-derive it from git history alone, it undersells how much shipped in a few large early commits.
- Don't scaffold, stub, or "prepare for" a later phase beyond the interfaces the spec's module boundaries require, unless the owner explicitly asks to jump ahead (as happened with the setup wizard and in-game polish before Phase 5 existed, and with Phase 5 itself before Phase 6's clock sync).
- Still explicitly deferred until the owner asks for them: Facebook OAuth, auto-update, tennis point display, padel.

## Stack constraints
- Kotlin, Jetpack Compose, minSdk 26, targetSdk 34+, landscape for the streaming/in-game screen; portrait for the setup flow (Home/Matches/wizard), switched via `requestedOrientation` — see `MainActivity.kt`'s `AppRoot`.
- Streaming: **StreamPack** (`io.github.thibaultbee.streampack`), pinned to 3.1.2 in `gradle/libs.versions.toml`. Do NOT hand-roll MediaCodec + an RTMP muxer. HaishinKit only with owner approval.
- No navigation library — the setup/wizard/in-game screen router is a plain sealed `Screen` enum + `when` in `MainActivity.kt`, deliberately avoiding a new dependency for a handful of screens.
- Ask before adding any dependency not named in the spec.

## Environment
- Windows 11, PowerShell/Git Bash — use `.\gradlew.bat` (or `./gradlew.bat` from bash) for all Gradle commands. `JAVA_HOME` needs to point at Android Studio's bundled JBR (e.g. `C:\Program Files\Android\Android Studio\jbr`) for CLI builds. `ANDROID_HOME`/`JAVA_HOME` env vars don't persist across tool-call boundaries in this setup — re-set them at the start of each new shell invocation before running Gradle.
- Streaming behavior must be verified on a **physical device** (USB debugging); the emulator is for compile checks only.
- For on-device UI automation, prefer `adb shell uiautomator dump` for exact element bounds over eyeballing screenshot coordinates — screenshots get downscaled for viewing and manual coordinate estimates have repeatedly been off by the scale factor (multiply displayed coords by the ratio shown in the image metadata, e.g. ×1.2, to get real device coordinates — easy to forget when a screenshot *looks* 1:1).
- **Web mirror** (`web-mirror/`): plain static HTML/CSS/JS, no build step. Firebase CLI (`firebase-tools`, installed globally via npm) deploys it — `firebase deploy --only hosting` from the repo root, using `firebase.json`/`.firebaserc` already checked in. Requires `firebase login` once per machine (interactive OAuth in the owner's own browser — never attempt this non-interactively on the owner's behalf). `.firebase/` (local deploy cache) is gitignored.

## Security
- Never hardcode, log, or commit stream keys, tokens, or keystores. Stream keys are runtime input only.
- Recent-target storage (`StreamTarget.kt` / `RecentTargetsStore`) persists ingest URLs for quick re-selection but deliberately never persists the stream key itself.
- Add keystore files and any local secrets to `.gitignore` in the very first commit.

## Working style
- At each phase/feature start: present a short plan (files to create and why), then WAIT for the owner's explicit go-ahead before writing code.
- Ask when the spec is ambiguous rather than guessing.
- Commit after each verified working step; small commits with clear messages. The owner keeps a last-known-good build at all times.
