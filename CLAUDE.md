**Phase 8 rebuilt on an external-browser OAuth flow (owner request, 2026-09-17)**: the owner asked for the Facebook login to open outside the app entirely — "a separate window or a browser" — so the app stays clean, and for the session to persist afterwards. The Facebook Login SDK cannot do this: `LoginBehavior` offers only the Facebook app, a Chrome Custom Tab, or an embedded WebView, and none of them is a fully external browser. Custom Tab was recommended and explicitly declined in favour of a real external browser after the trade-offs were laid out, so `LoginManager` is gone and the OAuth flow is hand-rolled; the SDK remains a dependency but is now used **only** for `GraphRequest`.
  How it works: `FacebookAuthManager.login()` opens `facebook.com/v21.0/dialog/oauth` via `ACTION_VIEW` + `FLAG_ACTIVITY_NEW_TASK`. Facebook will not accept a custom scheme as a `redirect_uri`, so it redirects to `https://scorecast-app-625c0.web.app/fb-auth.html` — a new static page in `web-mirror/` whose only job is to read `location.hash` in JS and re-emit it as `scorecast://fb-auth?...`, caught by the new `FacebookAuthRedirectActivity` (a trampoline, deliberately not an intent-filter on `MainActivity`, which is the landscape streaming screen with a live foreground service behind it). Because a URL fragment is never transmitted, **the token never reaches our hosting origin or its logs**. A `SecureRandom` state nonce is persisted to disk rather than held in memory, since Android is free to kill ScoreCast while the user types their password in another app.
  Also fixed two real defects in the old implementation, both of which made a saved login look absent: the token was read exactly once when the object was first touched — racing the SDK's async restore, and never re-read afterwards — and an expired token still presented as `LoggedIn` before failing Graph calls with an opaque message. `FacebookSessionStore` (new) now persists the session and the last Page, and `FacebookAuthManager.restore()` rehydrates it.
  **Verified on-device (Redmi 15, Android 16)**: compiles, installs, `scorecast://fb-auth` resolves to the redirect activity, and a forged redirect is rejected on the state nonce (`W FacebookAuth: Rejecting redirect: state nonce did not match`) with nothing written to `filesDir` and no crash. **Not verified: the entire happy path.** It was recorded here as blocked on two things, neither of them code: deploying `web-mirror/fb-auth.html`, and registering it under **Valid OAuth Redirect URIs** with Client OAuth Login and Web OAuth Login on. The deploy half is **done as of 2026-09-24** (see below). The dashboard half turned out to be moot — 2026-09-24 testing proved the app ID is rejected *upstream* of any redirect-URI check, so neither of those settings was ever the blocker. The old "Embedded Browser OAuth Login" toggle is irrelevant either way, since nothing goes through the SDK's login path.
  **Open risk:** Meta may have restricted `response_type=token` for apps of this vintage. If it has, the browser returns an error instead of a token and the only remaining route is authorization-code + PKCE, which needs the app secret and therefore the backend Phase 8 exists to avoid. This is unknowable until a real login runs.

**Phase 8 login attempted on-device for the first time (2026-09-24) — fails at Facebook's end with `PLATFORM__INVALID_APP_ID`, and the app's own code is positively cleared.** Tapping Facebook opens the external browser as designed and lands on `m.facebook.com/oauth/error/?error_code=PLATFORM__INVALID_APP_ID`, rendered as "Invalid app ID: The provided app ID does not look like a valid app ID." **Do not re-litigate the URL construction** — the exact launched URL was recovered from logcat and is correct in every part (`https://www.facebook.com/v21.0/dialog/oauth?client_id=135202131318789&redirect_uri=<the REDIRECT_URI, properly encoded>&response_type=token&scope=<the five permissions>&state=<nonce>`), and `client_id` matches `strings.xml` and the dashboard. The decisive test was a control: replaying the same request with a **made-up** app ID (`999999999999999`) proceeds normally to the login dialog, while the real one is bounced. A malformed request cannot explain an outcome where a fake ID gets *further* than the real one — Facebook is refusing **this specific app**, and "Invalid app ID" is just its generic wording for "this app may not use this dialog". Leading explanation, and it is one this file already listed as outstanding: the dashboard prerequisites for this flow were never done — **Client OAuth Login** and **Web OAuth Login** on, and `https://scorecast-app-625c0.web.app/fb-auth.html` added verbatim to **Valid OAuth Redirect URIs**. Two alternatives to rule out at the same time: (a) the app itself being disabled or policy-restricted by Meta, which produces the same error and is the one cause no amount of configuration fixes; (b) the app carrying **only** "Facebook Login for Business" and not classic "Facebook Login" — that one *does* come back to code, since Business Login rejects a consumer-style `scope=` call and needs a `config_id` from a dashboard configuration, i.e. `FacebookAuthManager.login()` would have to change. Check which product is installed before assuming a toggle fixes it.
  **Second blocker confirmed in the same pass: `https://scorecast-app-625c0.web.app/fb-auth.html` returns HTTP 404** (the origin itself is 200). It has never been deployed, so even once the dialog is fixed the redirect lands on a dead page and the token never reaches the app. Both blockers must clear together; fixing only the dashboard will look like no progress.
  **RESOLVED the same day — the Meta app `135202131318789` is dead on Facebook's side, and no code or OAuth setting can fix it.** The owner confirmed the installed product is classic **Facebook Login** (so the Business-Login/`config_id` branch above is ruled out — `FacebookAuthManager.login()` needs no change), and the error persisted. Three probes, none involving a user account, a session or a browser, settle it: (1) the OAuth dialog with correct parameters → `PLATFORM__INVALID_APP_ID`; (2) the same dialog with a **deliberately unregistered** `redirect_uri` of `https://example.com/nope` → *the identical error*, where a healthy app returns Facebook's well-known "URL Blocked" instead — proving Facebook rejects the app before it ever reaches redirect validation, and therefore that **Valid OAuth Redirect URIs / Client OAuth Login / Web OAuth Login are all downstream of the failure and cannot be the cause**; (3) a Graph call authenticated with an **app access token** (`APP_ID|CLIENT_TOKEN`, the most basic credential there is) → `code 190, "Error validating application. Cannot get application info due to a system error."`. Also note `response_type=code` with no `scope` fails identically, so nothing about the request shape matters. The app is deleted, disabled, or policy-restricted. **Re-checked 2026-10-15: still dead (same code 190 from the app-token probe); owner asked to create a new Meta app.** **Next step is the owner's, in the dashboard: look for a banner/alert on the app** (App Disabled, Restricted, an unresolved compliance or business-verification request). If it is unrecoverable, create a fresh Meta app, add Facebook Login, register `https://scorecast-app-625c0.web.app/fb-auth.html`, and the entire code change is the two strings in `app/src/main/res/values/strings.xml` — the request construction is proven correct and `FacebookAuthManager` does not move.
  **Keep the app-access-token probe as the standing health check for this app**, because it is fast, needs no device, no browser and no logged-in account, and cleanly separates "our request is wrong" from "the app is broken": `curl "https://graph.facebook.com/v21.0/<APP_ID>?access_token=<APP_ID>|<CLIENT_TOKEN>"`. A healthy app returns its own info; this one returns `code 190`. (The client token already ships inside the APK and is committed to the public repo by necessity, so using it this way exposes nothing new — but it is still not something to paste into a shared transcript casually.)
  **Partially narrows the `response_type=token` open risk above**: the bogus-ID control ran with `response_type=token` against `v21.0` and was *not* rejected for it, so the implicit flow is not blocked outright at the dialog. That is not a full clearance — Meta could still refuse to issue a token per-app at the next step — but it is no longer the leading suspect, and the app ID is.

**Hardened 2026-09-09 but NOT confirmed fixed — main device's Firebase push pipeline can silently stop syncing entirely (found 2026-07-16).** The original symptom: local state kept updating on-screen (clock counted down, a score tap went 10—11) while `homeScore`/`clockRunning` in the live database stayed frozen the whole time, with no crash and the app process confirmed continuously running. The prime suspect recorded here turned out to be a real defect on inspection: `observeLocalChanges()` ran on a bare `CoroutineScope(SupervisorJob() + Dispatchers.Main)` with no exception handler and no `try/catch` in the `collect{}` body, and `SupervisorJob` protects *siblings*, not a job from its own uncaught throw — so any exception there ended the push job permanently and silently for the life of the session. A second defect in the same block: `previousState = newState` ran *before* `pushDiff`, so a failed push advanced the baseline and lost that delta forever. Both are fixed (a `CoroutineExceptionHandler` plus error logging; the baseline now advances only `.onSuccess`, so a failed push re-sends its delta on the next local change). **The original trigger was never reproduced**, so this makes the failure logged rather than silent but does not prove it gone — re-run the two-device repro and watch logcat for `FirebaseSessionSync`.

**Real bug caught and fixed live in production this cycle (2026-07-09)**: the web mirror's score buttons could enter a self-sustaining write loop on iOS Safari — replacing the tapped button's DOM node (which happened on every score update, since our own write immediately echoed back through our own listener) could get an in-flight click re-targeted onto the new element, firing another write, rebuilding again, indefinitely, with no further taps needed. Reproduced against a live session (climbed into the tens of thousands within minutes), confirmed the Android app wasn't the source (force-stopped it mid-runaway, no effect — stopped only when the iPhone tab was closed), fixed by no longer rebuilding score buttons except when the sport actually changes, deployed, and verified stable with repeated taps landing exactly once each. Worth remembering as a general lesson for this codebase: never destructively rebuild a DOM element in direct response to its own click on that same event tick.

**Real bug found and fixed on-device this cycle (2026-07-15)**: the in-game screen's sliding scoring panel (`LiveOverlay` in `MainActivity.kt`) had no bottom clearance from the fixed bottom-right action row (battery/Hide panel/End match), which is drawn on top of it. On a shorter-aspect-ratio physical device, the Period/Clock rows rendered underneath those floating buttons, and touch dispatch went to whichever floating element was on top instead of the intended clock control — reproduced live: a tap aimed at "Start" instead advanced the Period stepper once and opened the End Match confirmation dialog another time. Fixed by giving the panel's scrollable content 64dp of bottom padding so its viewport stops above the floating row (mirroring the existing top-clearance `Spacer(40.dp)` pattern already used for the top bar). Trade-off: the panel no longer auto-scrolls to the clock, so on short screens it now sits below the fold and needs a manual scroll to reach — but it is then reliably tappable, confirmed via direct on-device tap producing correct start/stop transitions with no accidental Period/End-Match triggers.

**Two more real bugs caught and fixed live this cycle (2026-07-16), both found via actual Android↔Android pairing on two physical devices (not just code review)**:
1. **Runaway score-write feedback loop between paired devices** (`FirebaseSessionSync.kt`) — `attachListener()`'s `onDataChange` toggled a boolean `applyingRemote` flag true/false around applying a remote update, meant to stop the local-change collector from re-pushing that same echo. But the collector runs in a separately-launched coroutine reading `GameStateHolder`'s `StateFlow`, so the flag was already back to `false` by the time the collector actually observed the emission — the "local" diff it then computed got pushed straight back to Firebase as a fresh increment. Reproduced live: `awayScore` climbed past 2 million in under a minute across two paired devices before both apps were force-stopped to break the loop. Fixed by tracking the identity of the last-applied remote `GameState` object instead of a timing-dependent flag — the collector now skips a push only when the emission is referentially the exact remote object it just received, which has no race window. Verified: repeated pairing + scoring across both devices afterward with no runaway.
2. **Team name edits not saving** (`ScoringPanel.kt`) — the team-name `OutlinedTextField` pushed to `GameStateHolder`/Firebase on every keystroke, and each write's own echo (a full-state overwrite via `applyRemote`) could arrive mid-typing and clobber characters typed after that keystroke, landing on a stuck partial value (reproduced live: a name landed stuck at `"AW"` instead of the full typed name). Fixed by buffering keystrokes in local Compose state and committing to `GameStateHolder` (and thus Firebase) only on focus loss, removing the per-keystroke race entirely — also arguably better UX, since other viewers no longer see a name mid-edit. Verified on-device after the fix.

## Known deviation from spec
Spec §12 calls for `:streaming`, `:overlay`, `:capture`, `:core-state` etc. as separate Gradle modules. The codebase is currently a single `:app` module (package `com.scorecast.app`) — no module split has been done. Flag this if a future session wants to enforce the module boundary; it hasn't blocked anything so far.

Spec's distribution line calls for "Sideload only... privately hosted, in-app auto-update." Phase 9 instead uses the `scorecast` GitHub repo's public Releases API — the repo was deliberately flipped from private to public on 2026-07-28 specifically to enable this (a private repo would require an embedded token to read Releases, which can't be done safely client-side; full git history was scanned for secrets before flipping, confirmed clean). This was discussed and approved by the owner in-session as an alternative to standing up a small authenticating backend or a Firebase-Hosting-based alternative — flag if a future session wants the spec's wording updated to match, or wants to reconsider going private + backend-proxied instead.

Spec §10 ("Facebook — in-app destination picker") says the operator "logs in with Facebook inside the app (Facebook Login SDK)". As of 2026-09-17 login happens in the device's **external browser** and the SDK's `LoginManager` is not used at all — owner-requested, and reaffirmed after the alternatives and their costs were laid out. Two consequences worth spelling out:
- **The flow is OAuth's implicit grant (`response_type=token`), which OAuth 2.1 removes.** It was chosen because the alternative, authorization-code + PKCE, requires the app secret at the token-exchange step and therefore the secret-holding backend Phase 8 exists to avoid. If a backend ever appears for any reason, migrate this first. The registered Android **key hashes** the spec mentions are now irrelevant to login (they only mattered to the SDK's native/Custom Tab handlers); they still matter to nothing else, so leave them registered.
- **The redirect round-trips through our own Firebase Hosting origin**, because Facebook rejects custom schemes as `redirect_uri`. This puts a small piece of the auth flow in `web-mirror/`, which until now was purely the scoring mirror. Flag it if a future session wants the spec updated to describe this, or wants the page moved to its own hosting target.

Spec §10 ("Stream resilience") asks for adaptive bitrate "(StreamPack supports this)" and a degraded state. On StreamPack 3.1.2 that is only true for SRT: the bitrate regulator reads endpoint metrics, and `RtmpEndpoint.getMetrics()` throws `NotImplementedError("Not yet implemented")`. Every platform ScoreCast supports is RTMP(S), so the encoder stays at a fixed 4 Mbps and there is no congestion signal to drive a "degraded" state. Owner accepted skipping it (2026-10-09) rather than hand-rolling a heuristic. Revisit if a StreamPack release implements RTMP metrics, or if venues with weak uplinks need a manual low-bitrate option.

**Resolved 2026-10-15 — Facebook token at rest (spec §11).** `FacebookSessionStore` now encrypts the session (`facebook_session.bin`) with AES-256-GCM under a non-exportable Android Keystore key (alias `scorecast_facebook_session`); the old plaintext `facebook_session.json` is deleted on sight, and an unreadable file is deleted and treated as signed out. **Deviation from spec wording:** §11 names EncryptedSharedPreferences, but its library (`androidx.security:security-crypto`) is deprecated by Google in favour of the Keystore directly, which is what this uses — no new dependency (owner approved the fix; flagged in-session). Verified on the Redmi: a planted corrupt `.bin` and a legacy plaintext `.json` were both removed on launch, Settings showed "Not signed in", no crash. **The happy path (save a real token, reload it after restart) is unverified** — it needs a working Meta app, see below.

## Environment
- Windows 11, PowerShell/Git Bash — use `.\gradlew.bat` (or `./gradlew.bat` from bash) for all Gradle commands. `JAVA_HOME` needs to point at Android Studio's bundled JBR (e.g. `C:\Program Files\Android\Android Studio\jbr`) for CLI builds. `ANDROID_HOME`/`JAVA_HOME` env vars don't persist across tool-call boundaries in this setup — re-set them at the start of each new shell invocation before running Gradle.
- Streaming behavior must be verified on a **physical device** (USB debugging); the emulator is for compile checks only.
- **As of 2026-10-07 the attached test device is an OPPO CPH2565** (`6b868dbf`, Android 15, 1080x2400). Unlike the Redmi below, both `adb install -r -i com.android.packageinstaller <apk>` and `adb shell input tap/text/keyevent` work, so the UI can be fully driven from adb. Two quirks: right after install OPPO opens its own "Security test" app-scanner screen over everything (Back once, then `am start -n com.scorecast.app/.MainActivity`); and the soft keyboard covers the wizard's Next button while uiautomator still reports Next's bounds, so a tap silently lands on the keyboard — close it first. Use the Redmi notes below only if that device is reattached.
- The attached test device as of 2026-09-17 was a **Redmi 15** (`ac5ed006`, Xiaomi HyperOS, Android 16 / SDK 36, 1080x2340 @ 450dpi), **not** the CPH2059 (OPPO) referenced elsewhere in these notes — device-specific findings recorded against the CPH2059 may not transfer. Two HyperOS restrictions matter:
  - `adb install` fails with `INSTALL_FAILED_USER_RESTRICTED: Install canceled by user`, with the real reason visible only in logcat (`E PKMSImpl: MIUILOG- assertCallerAndPackage: uid=2000, installerPkg=null`). Xiaomi rejects an install that names no installing app; the "Install via USB" developer-options toggle being on is **not** sufficient. **Fix: always pass `-i`** — `adb install -i com.android.packageinstaller -r <apk>` succeeds immediately, with no Mi account and no on-device tap. The name does not need to be a real installer on the device.
  - `adb shell input tap`/`keyevent` fails with `SecurityException: Injecting input events requires ... INJECT_EVENTS permission`. That needs developer options → "USB debugging (Security settings)", which HyperOS gates behind a signed-in Mi account. Until then `uiautomator dump` and `screencap` work fine for *reading* the screen, but nothing can drive it — the UI-automation half of the workflow above needs the owner's hands.
- In Git Bash, absolute device paths passed to `adb shell` are rewritten by MSYS path conversion (`adb shell uiautomator dump /sdcard/ui.xml` lands at `/Files/Git/sdcard/ui.xml`). Set `MSYS_NO_PATHCONV=1` for those calls — but note it also stops the conversion of `JAVA_HOME` for `gradlew.bat`, which then fails with "Please set the JAVA_HOME variable". Either keep adb and Gradle in separate shell invocations, or set `JAVA_HOME` in Windows form (`export JAVA_HOME='D:\AndroidStudio\jbr'`), which works with the flag either way.
- For on-device UI automation, prefer `adb shell uiautomator dump` for exact element bounds over eyeballing screenshot coordinates — screenshots get downscaled for viewing and manual coordinate estimates have repeatedly been off by the scale factor (multiply displayed coords by the ratio shown in the image metadata, e.g. ×1.2, to get real device coordinates — easy to forget when a screenshot *looks* 1:1).
- **Web mirror** (`web-mirror/`): plain static HTML/CSS/JS, no build step. Firebase CLI (`firebase-tools`) deploys it — **reinstalled globally on 2026-10-07 (v15.32.1) and found already logged in**, so `firebase login:list` before assuming a login is needed — `firebase deploy --only hosting` from the repo root, using `firebase.json`/`.firebaserc` already checked in. Requires `firebase login` once per machine (interactive OAuth in the owner's own browser — never attempt this non-interactively on the owner's behalf). `.firebase/` (local deploy cache) is gitignored.

## Security
- Never hardcode, log, or commit stream keys, tokens, or keystores. Stream keys are runtime input only.
- Recent-target storage (`StreamTarget.kt` / `RecentTargetsStore`) persists ingest URLs for quick re-selection but deliberately never persists the stream key itself.
- Add keystore files and any local secrets to `.gitignore` in the very first commit.
- The `scorecast` GitHub repo is now **public** (flipped 2026-07-28 for Phase 9 — see the deviation note above). Nothing sensitive was ever committed (history was scanned before flipping), but this raises the bar further: never commit anything secret going forward, since there's no private fallback anymore.
- A release keystore exists for Phase 8/9 signing. **It was regenerated 2026-10-09** (PKCS12, alias `scorecast`, one password for store and key; certificate SHA-256 `637b2b8c206dad69f5db8f160cbf5a79490e2d215cd48410f31291577bb4bfdb`) after the owner lost the password to the original 2026-07-27 key. That cost nothing because no build signed with the old key was ever released, but it means **the release key hash registered with Meta in July is stale** — register the new one when a new Meta app is set up for Phase 8. From the first GitHub Release onward the key can never change again without breaking in-app updates for every install, so its password must live in a password manager. Gradle reads its path and passwords from `keystore.properties` at the repo root, which is gitignored along with `*.jks`/`*.keystore`; `keystore.properties.template` is the committed stand-in. Fill the real file in by hand in an editor — echoing the passwords into a shell puts them in shell history. Its local file path and passwords are known only to the owner and are intentionally not recorded in any version-controlled file — never run a command that would embed that password in a shell history, tool transcript, or committed file; have the owner run any keystore-password-bearing command themselves.
