## Anti-Patterns Verdict: **PASS**, and not narrowly

Measured across both surfaces: 0 gradients, 0 `background-clip:text`, 0 `backdrop-filter`/`.blur()`,
0 `box-shadow`, 0 Compose elevation overrides, 0 side-stripe borders, 0 bounce/elastic curves,
0 hero-metric blocks, 0 glassmorphism, 0 nested cards. Android has **zero animation of any kind** in
6,428 lines, and `grep "Color(0x"` returns nine hits, all inside the one owner-approved exception.

Nobody would look at this and say "AI made it." The layouts are irregular and task-shaped, and the
comments record real on-device failures rather than generic rationale.

The deductions are engineering defects and copy, not slop aesthetics:

- **Nine user-facing em dashes on Android**, three on web. `HomeScreen.kt:117` is the worst: the
  subtitle is `"— and score yourself"`, a dangling clause that only parses by leaning on the heading.
- **Two shipped dead-end placeholders.** `MainActivity.kt:845` tells the operator mid-broadcast that
  "Settings screen isn't built yet" while `SettingsScreen.kt` is 322 shipped lines routed from Home
  at `MainActivity.kt:140`. `WizardDestinationScreen.kt:122` ships "Break graphics, coming later (v2)".
- **Redundant copy.** `WizardTeamsScreen.kt:88` and `WizardDestinationScreen.kt:114` both label a
  component whose own two sections are already labelled. Three labels for two logo slots.

The detector's two findings (`overused-font`, `single-font`) are **false positives for this register**:
DESIGN.md explicitly commits to a system font stack so the page renders instantly on a poor
connection. Correct call, not a gap.

## P0 — Blocking

### P0-1. Production is two commits and roughly seven weeks behind the repo

**Category:** Deployment. **Verified by direct fetch, not inference.**

`https://scorecast-app-625c0.web.app` currently serves:

| Probe | Production | Repo |
|---|---|---|
| `--border` (dark / light) | `#3a3f4a` / `#d0d3d9` | `#6e7480` / `#80838a` |
| `[hidden]` rules in `style.css` | **0** | 1 |
| `color-toggle` in `index.html` | **0 occurrences** | present |
| `.step-btn` min-height | **40px** | 44px |

Consequences live for real users right now:

- With zero `[hidden]` rules and `.period-row, .clock-row { display: flex }` present, **`#clock-row`
  and `#shot-clock-row` are permanently visible for every sport.** A volleyball scorer sees a
  0:00 clock and a full set of Start / -5 / +5 / Rst shot-clock buttons, and can write junk
  `shotClock*` fields into the shared live session. This is the exact bug `AUDIT-2026-09-09.md`
  root-caused and fixed.
- Every button and input boundary measures 1.56:1 (dark) / 1.50:1 (light), failing WCAG 1.4.11.
- The 16 always-visible saturated swatches are still there.
- The `.step-btn` 40px target from before the 2026-08-05 sweep is still there, so commit `6f08072`
  never deployed either.

**Fix:** `firebase deploy --only hosting`. One command. It is the highest-leverage item in this
document by a wide margin, and it makes four separate prior findings disappear at once.

### P0-2. "Dismiss" on the stream-error banner destroys the live scoring UI mid-match

**Location:** `MainActivity.kt:233`, `:328`; `StreamerHolder.kt:152-154`. **Category:** Error recovery.

`showLiveUi = isLive || streamerState is Error`, and the comment directly above it states the
invariant: *"A dead stream must not yank the operator back to the setup panel mid-match... only Idle
returns to setup."* But `onDismissError = { StreamerHolder.acknowledgeError() }`, and
`acknowledgeError()` sets `State.Idle`. So the button labelled "Dismiss" does precisely what the fix
above it was written to prevent.

The operator is still scoring a live game. Tapping the innocuous button sitting immediately beside
"Retry" replaces the entire scoring surface with the pre-live setup form. `AUDIT-2026-09-09.md`
records this class of bug as fixed; the state machine was fixed and the button reaching into it
was not.

**Fix:** hold a UI-level `errorDismissed` flag in `StreamScreen` and keep `showLiveUi` true while a
match is in progress regardless of streamer state. Reserve the `Idle`-to-setup transition for the
End Match path only. Rename the button "Hide".

### P0-3. A set-winning tap is irreversible, and no UI anywhere can decrement `setsWon`

**Location:** `GameStateHolder.kt:110-134`. **Category:** User control and freedom.

Verified by grep: the only writes to `setsWonHome`/`setsWonAway` in the entire tree are
`GameStateHolder.kt:97-98` (reset on sport select) and `:127-128` (the increment inside
`addSetsGamesScore`). Every other reference is a read.

One mis-tap at 24-x banks a set the team did not win, zeroes both scores, advances the period,
changes the remaining win target, and burns the wrong tally into the video via
`ScoreboardOverlay.kt:107-108`. This affects **four of the eight shipped sports** (volleyball,
badminton, squash, table tennis). There is no warning before the tap, no confirmation, and no way
back short of restarting the match.

**Fix (either half is a legitimate ship):** (a) confirm the set-winning tap. It is the one tap in
the app that deserves a modal and the only consequential one that lacks it. (b) Add a bounded `-`
on the sets readout that reverses the last `addSetsGamesScore` transition.

## P1 — Major

### P1-1. The burned-in overlay shows a permanent "0:00" on every no-clock sport

`ScoreboardOverlay.kt:120-123` unconditionally appends `clockDisplay(...)`, which returns hardcoded
`0f` for `clockDirection == "none"` (`GameState.kt:47`). The app UI guards this in two places
(`ScoringPanel.kt:226`, `MainActivity.kt:649`); the renderer that reaches the audience does not.

`CLAUDE.md` records the 2026-09-09 pass as having fixed "the `clockDirection` guard its Android twin
was missing". The guard was added to the two UI surfaces and missed on the one that is burned into
the video. This is the only defect in this document that **every viewer** of a volleyball, badminton,
squash or table-tennis stream sees for the entire match. One conditional at `ScoreboardOverlay.kt:122`.

### P1-2. Camera-permission denial has no code path at all

`MainActivity.kt:245-249` is `if (startRequested && ok) { ... }` with no `else`. On denial nothing
happens: no message, no rationale, no Settings deep-link, and `startRequested` is never cleared. After
a permanent denial, **every subsequent Go Live tap is a silent no-op forever**, with no recovery
inside the app. `HomeScreen.kt:80-86` already has the deep-link pattern to copy.

### P1-3. Every control in the live view has a 1.07:1 boundary; the two error-recovery buttons are 1.00:1

`LiveTheme.CardBackground` is `#FFFFFF` and `LiveTheme.Background` is `#F7F7F3`
(`LiveScoringView.kt:98-99`), so every `LiveSmallButton` (`:177`) and both period steppers (`:384`,
`:394`) sit at **1.07:1** against their container. Inside `LiveErrorBanner`, whose own surface is also
`CardBackground` (`:76`), Retry and Dismiss are white on white at **1.00:1**. Fails WCAG 1.4.11.

`LiveTheme.CardBorder = #E3E1DB` is declared at `:100` and, verified by grep, **used nowhere**. The fix
is already written and unwired, though `#E3E1DB` on `#F7F7F3` is only ~1.2:1 and needs darkening to
roughly `#A9A6A0` first. This is the same correction DESIGN.md applied to `--border` on 2026-09-09;
the exception screen was left out of that pass by accident.

### P1-4. Wizard sport and platform selection is conveyed by background alpha alone, at 1.46:1

`WizardSportScreen.kt:41-46`, `WizardPlatformScreen.kt:47-72`. Selected is
`primary.copy(alpha = 0.25f)`, unselected `surfaceVariant.copy(alpha = 0.4f)`. Composited against
`background` these are `#3A3649` vs `#191C23` in dark (**1.46:1**) and `#D2CBE2` vs `#F1F2F4` in light
(**1.40:1**). No border, no checkmark, no `Role.RadioButton`, no `semantics { selected = ... }`.

Fails WCAG 1.4.1, 1.4.11 and 4.1.2. The codebase already solved exactly this for the colour swatches
(`ScoringPanel.kt:119-122`); the tile grids were missed.

### P1-5. Two fixed-height containers provably overflow, taking real controls off-screen

Both computed from declared `dp` against the ~360dp landscape height the file itself asserts
(`MainActivity.kt:498-499`, `:995-996`).

- **Live-view top strip.** `MainActivity.kt:547` is `fillMaxHeight(0.38f)` = 136.8dp. Contents:
  48dp Switch row + 44dp countdown row 1 + 4dp spacer + 44dp countdown row 2 + 12dp padding =
  **152dp**. The `-30`/`+30`/`Rst` row is laid out past the parent's bottom edge, the sibling
  Column below paints over it, and hit-testing outside the parent's bounds fails.
- **Fullscreen side column.** `MainActivity.kt:1010-1049` totals ~354dp before the battery text row
  is measured, putting the mic button ~10dp off-screen.

Neither container clips nor scrolls. Note the comment at `MainActivity.kt:544-546` warns about
exactly this and records the last fix as re-tuning the fraction from `0.32f` to `0.38f`. Retuning a
magic number is why it came back.

### P1-6. Sustained overlay bitmap churn, and a coroutine leak that can tear down a live stream

- `CameraOverlayVideoSource.kt:125` combines an unconditional 250ms ticker, so
  `ScoreboardOverlay.create` runs 4x/second for the whole match regardless of whether anything
  changed. Each call allocates a 1280x720 ARGB_8888 bitmap (`ScoreboardOverlay.kt:23`) = 3.69 MB,
  i.e. **~14.7 MB/s of never-recycled garbage**, plus ~6 Paints and two `Typeface.create` per call.
  On a phone already running Camera2, EGL and a hardware encoder this is the most likely cause of
  dropped frames. (Carried forward from `AUDIT-2026-09-09.md` P1-4, still open.)
- `StreamerHolder.kt:123` launches `s.throwableFlow.collect { fail(it) }` without storing the Job;
  `teardown()` never cancels it and `scope` belongs to a process-lifetime singleton. Every
  start/stop cycle adds another. Worse, `fail()` calls `teardown()`, which reads the **shared**
  `streamer` field rather than the one that threw, so a throwable from a released streamer can
  release whichever stream is live at that moment.

### P1-7. The score is the smallest it is anywhere, on both dedicated scoring surfaces

`ScoringPanel.kt:329-331` renders the score at `titleMedium` (~16sp) in a fixed `width(32.dp)` box,
one step above the panel's own "Scoring" header. `MirrorScoringScreen.kt:60` is literally just
`ScoringPanel()`, so the remote scorer's entire device shows the score at 16sp.

DESIGN.md §3 defines a **Display** role (700 / 2.5rem / tabular) explicitly for "the score itself,
the single most-glanced-at element". Android never uses `displayLarge`/`displayMedium` anywhere, and
`grep fontFeatureSettings` returns **zero hits app-wide**, so the Tabular Clock Rule is entirely
unimplemented on Android and the clock reflows horizontally on every tick.

### P1-8. Web: an unknown sport silently degrades to "Generic" with the wrong scoring rules

`app.js:183-185` falls back to `DEFAULT_SPORT` and `:188` then displays "Generic". `sports.js` is a
**hand-maintained duplicate** of `app/src/main/assets/sports/*.json` (its own header comment says so).
A sport added on Android but not mirrored here scores with increments `[1]` and the flat model,
silently, on a live broadcast, with nothing warning the scorer that the rules are wrong.

### P1-9. Web: an offline tap is visually identical to one that reached the broadcast

`pushUpdate` (`app.js:505-511`) has a `.catch` but no success path, and there is no per-write pending
state anywhere. Because the RTDB SDK applies `increment()` optimistically to its local cache and
re-fires `onValue`, **the score moves on screen whether or not the write landed.** The only
differentiator is 0.85rem of amber text at the top of the page.

PRODUCT.md sets the bar at "every tap lands exactly once... even on a flaky connection" and its
Degrade Honestly principle explicitly prohibits showing stale state as live. Right now the mirror's
most reassuring signal is also its least trustworthy one. `--pending` already exists and already
means "not settled".

### P1-10. Web: joining costs 45 hand-typed hex characters, and the share path does not prefill

`SessionCode.kt:25-26` makes the code a full UUIDv4 plus 8 characters = **45 characters**.
`MainActivity.kt:796` shares `"...web.app  Code: <45 chars>"` as plain text, and `app.js` has **no
URL-parameter handling** (all 605 lines read), so the scorer retypes it by hand. Compounded by
`app.js:27,98` using `sessionStorage`, which is per-tab: close the tab mid-match and they retype all
45 characters.

**Fix:** share `https://...web.app/?code=<code>` and parse `?code=` on load. This removes the
worst step in the product's only onboarding flow, and it is maybe fifteen lines.

## P2 — Minor

**Android**

- **Chip status text over video fails 4.5:1 even in the best case.** `MainActivity.kt:873-882` uses a
  55%-opaque black scrim over arbitrary footage. In light system mode, `onSurfaceVariant` `#545B68`
  measures 3.07:1 against fully-black footage and **1.44:1** against white footage. Make the chip
  background opaque and pick text colours for that fixed backdrop.
- **Score `+N` buttons carry no accessible name** (`LiveScoringView.kt:289-297`), while their `-`
  sibling twelve lines earlier correctly says "Decrease $teamName score by 1". Three
  `OutlinedTextField`s for team names have no `label` at all (`ScoringPanel.kt:311`,
  `LiveScoringView.kt:231`, `WizardTeamsScreen.kt:106`).
- **No `Switch` in the app has a programmatic label**, and the pairing switch can never be turned off:
  `MainActivity.kt:596` discards `onCheckedChange`'s boolean, so toggling off re-opens the dialog and
  snaps back on. There is no un-pair path short of End Match.
- **Disk I/O on the main thread inside composition on six screens**, worst at `RecordingsPanel.kt:77-78`
  (two `stat()` syscalls per recording per recomposition, in the in-game setup surface).
- **Firebase session creation executed inside `remember`** (`MainActivity.kt:790`), a phase Compose is
  free to abandon and re-run. It also means one mis-tap on the pairing switch publishes game state to
  a network session with no confirm.
- **`configChanges` omits `uiMode`** (`AndroidManifest.xml:43`), so a system dark/light flip recreates
  the Activity, and `pendingTarget`/`mirrorSession` are plain `remember` rather than `rememberSaveable`,
  so the operator's chosen platform, ingest URL and stream key silently reset.
- **Fixed heights and widths clip at raised font scale.** `Modifier.height(44.dp)` on nine Material
  buttons and `width(52.dp)` on the live clock readout: at 1.5x font scale `"10:00"` needs ~60dp.
- **"Recent" ingest-URL rows are ~24dp tall** (`WizardDestinationScreen.kt:98-107`), stacked directly
  on each other, so a mis-tap silently selects the wrong URL.
- **31 sites standardise on 44dp**, 4dp under Android/Material's 48dp guideline. Deliberate and
  internally consistent, but it matters where four sit shoulder-to-shoulder (`MainActivity.kt:607-641`).

**Web**

- **The error line shoves the entire scoring UI downward at the moment of failure.** `#score-error`
  (`index.html:33`) sits above every control and is toggled via `hidden`, which `style.css:24` now
  makes `display: none`. Showing it inserts a line into normal flow and translates every button
  below it down by ~25px, exactly when the scorer is reaching back to re-tap. Same class of hazard as
  the iOS rebuild loop this codebase already paid for. Reserve the height instead.
- **Both colour-picker toggles have an empty accessible name** (`index.html:70-74`, `:88-92`): they
  contain only an empty span and an `aria-hidden` caret. A screen reader announces "button, collapsed".
  The swatches *inside* were correctly labelled (`app.js:398`); the control that reveals them was missed.
- **4 of 8 unselected swatches fail WCAG 1.4.11 in dark mode.** `style.css:280` is
  `border: 2px solid transparent`. Against `--card` `#1c1f26`: `#374151` 1.61:1, `#1E40AF` 1.90:1,
  `#B91C1C` 2.56:1, `#7C3AED` 2.91:1. Use `var(--border)` for unselected, which already clears 3:1

- **`text-transform: uppercase` on the team-name input is a WYSIWYG lie.** `style.css:212` uppercases
  visually, `app.js:557` commits the raw typed string, and `ScoreboardOverlay.kt:107-112` draws it

- **"Leave session" is ~18px tall** (`style.css:140-146`, `padding: 0`, no min-height), failing WCAG

- **`.color-toggle` is the only interactive element with neither a `:focus-visible` ring nor a

- **No width media query anywhere**; `main` is capped at 480px (`style.css:35`). The confirmed primary
  persona is at a laptop, so the console is a 480px strip on a 1440px screen with the score far

- **"Rejoining your previous session…" is rendered as an error.** `app.js:595` writes a benign status

## Patterns & Systemic Issues

1. **Fixes land in the state machine but not in the control that reaches into it.** P0-2 is the
   clearest case: `showLiveUi` was correctly hardened and its comment states the invariant, while the
   Dismiss button wires straight past it. P1-1 is the same shape: the `clockDirection` guard was added
   to two UI surfaces and missed on the renderer that reaches the audience. Both were recorded as
   fixed. **When a fix is written, grep for every caller that can re-enter the state it protects.**

2. **Fixed-fraction and fixed-`dp` heights used as layout budgets the content then busts.** Both P1-5
   overflows are computable from declared values alone. The codebase knows this failure mode. Four
   separate comments document prior instances, and each time the fix was to re-tune a magic number
   rather than remove the fixed constraint.

3. **Work with real cost executed during composition.** QR generation, `ScoreboardOverlay.create` on
   every keystroke in the wizard preview, `SessionHolder.ensureSession()` with its Firebase write, and
   six file-system reads. Composition is being treated as a place to *do* things rather than describe them.

4. **Contrast was audited for text but never for component boundaries inside the exception screens.**
   The 2026-09-09 pass correctly raised `--border`/`outline` and documented the math. `LiveScoringView.kt`
   declares `CardBorder`, never wires it, and paints every control `#FFFFFF` on `#F7F7F3`. The web
   mirror has the same gap in its swatches. The rule exists; both exceptions to it were exempted by accident.

5. **Accessibility applied per-call-site rather than per-component, so coverage is uneven.**
   `SmallButton` takes an optional `contentDescription`: `RecordingsPanel` passes it at all three
   sites, `ScoringPanel` at three of eleven. `LiveTeamCard`'s `-` is labelled, its `+N` siblings are
   not. On web, the swatches got `aria-label`s and the toggle that reveals them got none. **Making the
   description a required parameter closes all of these at once.**

6. **Two hand-maintained sources of truth for scoring rules on a live broadcast.** `sports.js`
   duplicates the Android sport JSON by hand, acknowledged in its own header. P1-8 is the concrete
   consequence.

## Positive Findings

- **The wizard preview is the production renderer, not a mock.** `WizardTeamsScreen.kt:50-51` calls
  the exact `ScoreboardOverlay.create` the GL compositor burns into the encoded frame. There is no
  second implementation to drift, and every future overlay change is verified in setup for free. This
  is the highest-leverage decision in the codebase.
- **Anchor-based clock state is genuinely well designed.** Storing `startedAtMs` + `baseRemainingSeconds`
  and deriving the display is why start/stop is idempotent, why cross-device skew is solvable at all,
  and why the UI can tick without owning any truth. Accidental clock start/stop is the best-handled
  interaction in the app: fully reversible and lossless.
- **Theme discipline is excellent.** Nine `Color(0x` hits in 6,428 lines, all inside the documented
  exception. All five `surfaceContainer*` tiers explicitly pinned with a comment explaining why.
  Zero literal hex in any CSS rule, with full dark/light parity on every semantic token.
- **Text contrast passes 4.5:1 in both themes for every web pair I computed** (muted 6.31/7.07 dark,
  6.83/6.22 light; accent 6.32/5.76 light; accent-ink 7.26 dark; danger 5.62/5.12; ok 6.87;
  pending 5.62), and `--border` clears 3:1 against all three surfaces in both themes. The 2026-09-09
  colour work holds up under independent recomputation.
- **The `weight(1f) + verticalScroll` bug class appears fully eliminated.** Every `verticalScroll` site
  was checked; no remaining instance of the pattern.
- **`FirebaseSessionSync` is the best-hardened file in the codebase.** Identity-based echo suppression,
  a `CoroutineExceptionHandler`, and an `.onSuccess`-gated baseline advance, each with a comment naming
  the exact live incident that motivated it. `OverlayCompositor`'s EGL lifecycle is likewise correct,
  with a `@Volatile released` guard checked at the top of every posted block.
- **Tap confirmation on web is solved at three independent layers**, including `app.js:25`, a no-op
  `touchstart` listener registered purely because WebKit will not honour `:active` without one. That
  is a quirk most developers never discover, and its absence would have silently killed tap
  confirmation on exactly the iPad the fallback scorer is most likely holding.
- **Progressive disclosure on web is driven by the live session's own sport config**, not a settings
  screen, which is why the volleyball screen is 11 controls instead of 22.
- **Destructive actions are consistently confirmed and consistently coloured** across all five paths,
  several naming the exact count or file size at risk.
- **The anti-rebuild lesson was generalised into a rule, not just patched.** `app.js:387-389` and
  `:404-406` apply the discipline preemptively to components that never had the bug.

## Persona Red Flags

**Sam, the courtside operator** (phone mounted at a school gym, filming and scoring simultaneously,
outdoors in daylight):

- Denies the camera permission once by reflex. Go Live is now a silent no-op forever with no message (P1-2).
- Loses the stream, taps the button next to Retry, and the scoring panel is replaced by a setup form (P0-2).
- Cannot see which sport is selected in the wizard at 1.46:1 in daylight (P1-4), and cannot see the
  edge of any clock button on the live screen at 1.07:1 (P1-3).
- Nineteen identical 44dp targets. The score, tapped fifty times a match, is the same size as Share.
- Fullscreen is the mode used while framing the shot, and it contains **zero scoring controls**. Every
  point costs a round trip through a 44dp toggle wedged between three other icons.

**Riley, the volunteer remote scorer** (laptop, first time, joined five minutes before tip-off):

- Hand-types 45 hex characters read off someone else's phone, into an unfocused field whose only
  format guidance is `sessionId:joinToken` (P1-10).
- Is at a keyboard, and the product knows it (DESIGN.md reasons explicitly that this user is
  keyboard-first), yet there is **not one key binding in `app.js`**. Every point is a mouse trip.
- On production today, sees shot-clock controls on a volleyball match and can start a phantom
  shot clock (P0-1).
- Mis-taps `+1` at 24-23. The set banks, both scores zero, and nothing can undo it (P0-3).
- Closes the tab by accident. `sessionStorage` is gone; retype all 45 characters.

## Questions Worth Sitting With

1. **Why is the score-increment button the same 44dp as the Share icon?** The web mirror already ran
   this experiment and went to 64x56 after live use, because they are "the single most-tapped control
   on the page". The operator, who is also holding a camera and watching a game, got the version the
   remote scorer at a desk rejected.
2. **The clock got five recovery affordances and a manual-edit dialog. The score got `-1`.** Both are
   game state that a mistake corrupts on air, and the score is tapped ten times more often. What breaks
   if `GameStateHolder` keeps a bounded stack of recent snapshots and the live screen gets one
   "Undo last" that reverses any action, including the set win nothing else can touch?
3. **Fullscreen is described in the code as the operator's real working surface, and it cannot score.**
   Are these actually two modes, or is the truth that there is one working screen with a video pane
   that should resize, where camera controls and game controls coexist rather than alternate?
