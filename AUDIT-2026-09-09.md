## FIXED in this session (Wave 1)

### 1. `[hidden]` was inert on three web-mirror rows — root cause of a documented open bug

`web-mirror/style.css` had **no** `[hidden]` rule, and `.period-row, .clock-row` declared
`display: flex`. An author-origin `display` beats the UA stylesheet's `[hidden]{display:none}` at any
specificity, so these toggles never did anything:

- `app.js:211` `period-row`
- `app.js:225` `clock-row`
- `app.js:231` `shot-clock-row`

`app.js:201` (`#sets-row`) worked only because `.sets-row` sets no `display` — which is exactly why
only the Clock row was ever noticed as broken.

Two consequences that had **not** been reported: the Shot Clock row and its Start/-5/+5/Rst buttons
rendered for **every sport**, letting a remote scorer start a phantom shot clock on a volleyball match
and write junk `shotClock*` fields into the shared session; and the Period row could never be hidden.

**Fix:** added `[hidden] { display: none !important; }` near the top of `style.css`.
**Status: NOT yet verified against a live paired session, and NOT yet deployed.** Needs a
volleyball/badminton session on the deployed site to confirm all three rows are absent.

### 2. Android twin of the same bug: no `clockDirection` guard on the live countdown

`ScoringPanel.kt:141` guards with `if (state.clockDirection != "none")`. The `LiveCountdownSection`
call in `MainActivity.kt` had no such guard (only the shot clock was gated, on `config.shotClockSeconds`).
Volleyball, badminton, squash and table tennis operators saw a permanent "COUNTDOWN 0:00" with a live
yellow play button and adjusters that could never do anything.

**Fix:** guarded the countdown on `state.clockDirection != "none"`, and wrapped the whole Row so it
collapses when neither the countdown nor the shot clock applies. `config.shotClockSeconds` was hoisted
to a local val to preserve the smart cast.
**Status: compiles clean. NOT verified on-device.**

### 3. `FirebaseSessionSync` push collector could die silently

`observeLocalChanges()` ran on a bare `CoroutineScope(SupervisorJob() + Dispatchers.Main)` with no
exception handler and no `try/catch` in the `collect{}` body. `SupervisorJob` protects *siblings*, not
a job from its own uncaught throw, so any exception ended the push job permanently with no crash and
no log — local state would keep updating on-screen while nothing reached Firebase again. That matches
the 2026-07-16 report exactly.

Second defect in the same block: `previousState = newState` executed **before** `pushDiff`, so a
failed push advanced the baseline and lost that delta forever.

**Fix:** added a `CoroutineExceptionHandler` to the scope; wrapped the push in `runCatching` and moved
the baseline advance into `.onSuccess`, so a failed push keeps the old baseline and the next local
change re-sends the missed delta. Added a `TAG` and error logging.
**Status: compiles clean. The 2026-07-16 bug is NOT confirmed fixed** — this hardens the collector and
makes the failure loggable rather than silent, but the original trigger was never reproduced. Re-run
the two-device repro and watch logcat for `FirebaseSessionSync`.

## FIXED in this session (Wave 2 — both P0s)

### 4. A stream failure silently destroyed the live UI

`StreamerHolder.fail()` set `State.Error`, then called `stop()`, whose `finally` immediately
overwrote it with `Idle`. Since `isLive = Live || Starting` (`MainActivity.kt:229`), the moment the
stream died the entire scoring overlay was replaced by the pre-live panel reading "Status: idle" —
mid-match, no explanation, cause discarded.

**Fix:** extracted a private `teardown()` that releases the streamer without touching `state`.
`stop()` is now `teardown()` + `Idle`; `fail()` tears down **first** and publishes `State.Error`
**last**, so nothing can clobber it. Added `acknowledgeError()`. In the UI, a new `showLiveUi`
(`isLive || Error`) keeps the live screen mounted on failure, and a new `LiveErrorBanner`
(`LiveScoringView.kt`) shows the message in place with **Retry** and **Dismiss**. Only `Idle`
returns to setup.
**Status: full `assembleDebug` succeeds. NOT verified on-device** — needs a real stream failure
(kill the network mid-broadcast) to confirm the banner appears and Retry works.

### 5. No indication of whether you are live, in the default live view

The only signal was a dot hardcoded to `LiveTheme.DangerText` regardless of state, beside a timer
reading `00:00` until `liveStartedAtMs` was set. Starting, Live and Idle-after-failure were
pixel-identical.

**Fix:** `LiveBottomBar` now takes `streamerState` and renders a colour-plus-text pair per
DESIGN.md's Status Indicator rule: `● LIVE` (danger) + elapsed, `● Starting…` (new
`LiveTheme.PendingText`, DESIGN.md's own light-mode `status-pending` `#8f5300` at 5.61:1 rather than
an invented amber), `● Off air` (danger on error, muted on idle). The elapsed timer now shows only
when actually Live.

Also fixed in the same pass: the **fullscreen** chip had the same defect and would have read
"● LIVE" over a dead stream once Error kept the UI mounted; it is now state-driven, keeping the
pure-red/yellow tally convention for Live/Starting and theme colours for off-air. The orphaned
`isStarting` val was removed.
**Status: compiles clean. NOT verified on-device.**

### 6. `LiveSmallButton` was ~29dp (P1, fixed opportunistically)

A raw `Box` with 6dp padding and 12sp text, used for 7 live-critical clock controls while every
sibling in the file uses 44dp. Added `defaultMinSize(44.dp, 44.dp)` + `contentAlignment = Center`
(not `.size`, so a wide label still governs width).
**Status: compiles clean. NOT verified on-device.**

### 7. Team-colour swatches collapsed; the white-ring bug fixed at every call site

Sixteen always-visible saturated 44dp swatches were the densest and least time-critical group on
the live scoring screen, and the single root cause of 4 of the 6 web cognitive-load failures.

**Fix (Android):** one shared `TeamColorPicker` in `ScoringPanel.kt` — a collapsed current-colour
chip that expands the eight presets inline on tap, staying open until tapped again. It replaces the
duplicated inline implementations in `ScoringPanel.kt` and `LiveScoringView.kt`, which addresses the
"no shared selectable component" systemic finding for this control. Its `ringColor` is a required
parameter precisely so the `Color.White`-on-white bug can't be reintroduced per call site.

**Fix (web):** `.color-picker` chip + `[hidden]` preset row in `index.html`/`style.css`, with the
toggle wired in `buildColorSwatches`. The toggle only flips `hidden`/`aria-expanded` and never
rebuilds a node in response to a click on that node, per the iOS Safari runaway-loop lesson. Also
added `aria-pressed` to each swatch (P2) — visual selection was already a border rather than colour
alone, but assistive tech saw eight identical plain buttons. Note this row is the first real
consumer of the `[hidden]` fix from Wave 1.

**`WizardTeamsScreen` deliberately keeps its swatches expanded** — choosing the colour is that
step's entire purpose, so collapsing would bury the primary task. It took the other two fixes: the
`onSurface` ring, and the selection semantics it was missing entirely.

**Status: `assembleDebug` succeeds; `node --check` passes on `app.js`. Neither surface verified
by eye. The web change is NOT deployed.**

### 8. Shot-clock interval leak (P2)

`detachListeners()` called `stopClockTicking()` but never `stopShotClockTicking()`, so leaving a
basketball session with the shot clock running left a 500ms interval firing for the life of the tab.
One line. **Status: not verified at runtime.**

## FIXED in this session (Wave 3)

### 9. `scoreboardLight` was reset by every remote update (not in the original findings)

Found while committing Wave 3, not by any of the four assessments. `attachListener`'s `onDataChange`
applied the remote `GameState` wholesale, but `scoreboardLight` is a local-only display preference
that is deliberately never written to Firebase — so `toGameState()` always produced the class default
(`false`/dark). Every remote update therefore flipped the burned-in overlay back to dark, **including
the echo of this device's own score writes**, so on a paired session the operator's light/dark choice
could not survive a single score tap. `ScoreboardStylePrefs` persisted it across restarts, which is
probably why this was never traced: it always came back correct on relaunch.

**Fix:** carry the current local value forward with `remote.copy(scoreboardLight = ...)` before
applying, and use that same object as `lastAppliedRemote` so identity-based echo suppression still
matches. **Status: compiles clean. NOT verified on a live paired session.**

### 10. P1-2 — button/input boundaries raised to WCAG 1.4.11 (3:1)

`--border`/`outline` went from `#3a3f4a`/`#d0d3d9` to `#6e7480`/`#80838a`: **1.56:1 → 3.51:1** dark
and **1.50:1 → 3.80:1** light against Card Surface, and both clear 3:1 against Void and Pill Surface
too. Changed in all three places the One Brand, Two Renderers rule requires — `DESIGN.md`
frontmatter *and* prose, `web-mirror/style.css` (both themes), and `Theme.kt`'s `outline` role in
both schemes. **Status: recomputed by hand; not yet re-measured in a browser, not deployed.**

### 11. P1-5 — wizard platform grid no longer clips its last row

`WizardPlatformScreen.kt`'s `Modifier.height(280.dp)` became `Modifier.weight(1f)`, letting the grid
take the real available height inside `WizardScaffold`'s already-bounded column. **Status: compiles
clean. NOT verified on-device — this is the fix most worth eyeballing on the CPH2059, since it is a
layout change to a screen that has to fit five tiles.**

### 12. P1-6 — destructive confirms now render in the error role

All five sites: `MainActivity.kt`'s End match, `MatchesScreen.kt`'s delete-match, and
`SettingsScreen.kt`'s three clear/delete rows. Also closes the One Accent Rule violation, since
DESIGN.md's mapping table already assigned "End match" to `error`. **Status: compiles clean.**

### 13. P1-7 — deleting a recording now confirms

Same `AlertDialog` pattern as `MatchesScreen`, naming the file and size (both already computed).
`SmallRecordingButton` gained a `contentDescription` parameter, so "▶", "Share" and the
now-spelled-out "Delete" all announce a real name. **Status: compiles clean.**

## OPEN — P1

**P1-1 — Set-winning tap is unconfirmed, unwarned, irreversible (web).**
`app.js:468-481` zeroes both scores, banks the set and advances the period. Afterwards `-1` is disabled
because the score is 0 (`app.js:217`), and the sets row is a read-only readout (`index.html:84-89`) —
despite DESIGN.md:217 claiming it is "fully live and editable". Four of eight sports use this model.
*Fix:* warn on the set-point tap (relabel to note it wins the set, require a confirming second tap),
add decrement steppers to `#sets-row`, and keep `#home-minus` enabled briefly after a set win.

**P1-4 — 3.69 MB bitmap allocated 4x/second for the entire broadcast.**
A 250ms ticker (`CameraOverlayVideoSource.kt:124-133`) drives `ScoreboardOverlay.create()`, which opens
with `Bitmap.createBitmap(1280, 720, ARGB_8888)` and never recycles: **14.7 MB/s** of GC churn on a
device simultaneously running Camera2, GL compositing, H.264 and RTMPS. Plausible contributor to the
unroot-caused RTMP disconnects.
*Fix:* reuse one bitmap per resolution (`eraseColor(0)` + redraw); gate the ticker on actual change —
the clock needs 1 Hz, and a stopped clock with no state diff needs zero redraws.

**P1-8 — Push collector hardening still needs its live repro.** See Fixed #3 above.

## Systemic patterns

1. **Selection state is unsolved on Android: 5 sites, 3 distinct failure modes, only 1 correct.**
   No shared selectable component, so each site re-derived it. `WizardSportScreen.kt:37-50`,
   `WizardPlatformScreen.kt:42-67` and `MainActivity.kt:1089-1091` convey selection by **colour tint
   alone** with no `selected` semantics — a direct PRODUCT.md "never color-only" violation.
2. **Three parallel button implementations for one job.** `SmallButton` (44dp, has `contentDescription`),
   `SmallRecordingButton` (44dp, none), `LiveSmallButton` (~29dp, none). The touch-target regression is
   a direct consequence of the duplication.
3. **Four uncoordinated `while(true){delay()}` tickers while live** (4 Hz, 2 Hz, 2 Hz, 1 Hz), all
   rendering clocks that change at most once per second.
4. **Emoji-as-icon system, ~60% labelled.** 20+ glyph controls, 8 unlabelled. Emoji ignore `color =`
   and render at OS-dependent size and weight, so there is no consistent optical weight.
5. **Both surfaces have full write authority and near-zero write reversibility.** The mirror can start
   clocks, rename teams and end a volleyball set with no undo for any of it. This single theme explains
   the lowest scores on both cards (web H3 = 1, H7 = 1).

## What is genuinely well built

- **The colour system is verifiably drift-free.** All 21 tokens match across DESIGN.md's frontmatter,
  `style.css` and `Theme.kt`, in both themes. Zero hardcoded hex in any CSS rule. "One Brand, Two
  Renderers" is actually enforced, not aspirational.
- **Light-mode contrast was done properly, not by lightness-inversion.** Recomputed: `--muted` on
  `--bg` = 6.21:1, `--ok` = 6.86:1, `--pending` = 5.61:1, accent fill with accent-ink = 7.26:1.
- **`Theme.kt` encodes two non-obvious Material3 traps as fixes** — pinning all five `surfaceContainer*`
  tiers, and the root `Surface` without which `LocalContentColor` never picks up the theme.
- **The hard-won concurrency fixes are correct and carry their bug history inline** — identity-based
  echo suppression, on-blur name commit, and the "never rebuild a DOM node in response to its own
  click" guard.
- **Sub-44dp targets were fixed by wrapping, not inflating** — a 44dp invisible Box around a 16-22dp
  visual dot, with `horizontalScroll` to absorb the width.
